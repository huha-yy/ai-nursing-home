## 1. 方案摘要

本方案面向养老院、福利院等园区机构的本地部署场景。服务器使用 DHCP 自动获取内网 IP，不在设备端手动配置固定 IP；每家机构分配一个永久不变的真实域名，并将该域名印制成二维码。服务器的内网 IP 发生变化时，设备上的独立动态 DNS 更新程序自动修改域名记录，用户继续扫描原二维码访问，无需知道服务器 IP。

业务数据库、居民档案、照片、健康数据、模型输入输出和业务日志全部保存在养老院本地服务器。服务器不接受互联网主动连接，只允许按白名单访问动态 DNS、证书、时间同步和经过审批的外部数据源。

推荐访问形式：

```text
二维码（永久不变）
https://yl-a7k3.edge.example.com
             |
             v
公共 DNS 返回当前养老院内网 IP
             |
             v
院内 IP 192.168.10.83，HTTPS 443
             |
             v
养老院本地应用、数据库和模型
```

DNS 只负责把固定名称映射到当前 IP，不负责打通不同 VLAN、访客网络或互相隔离的路由器。因此，项目交付时必须验证工作人员使用的 Wi-Fi 能够访问服务器所在网络。

## 2. 建设目标

1. 服务器插网线后自动获取网络地址，无需在设备上手动配置固定 IP。
2. 用户使用个人手机浏览器扫码访问，无需安装 App、输入 IP 或记忆端口。
3. 二维码永久不变，服务器 IP 变化后能够自动恢复访问。
4. 业务数据全程在养老院内网存储和处理，不通过云端中转。
5. 互联网不能主动访问服务器，外网访问采用最小权限白名单。
6. 断网时已运行的本地业务继续可用，并提供本地应急访问方式。
7. 能够识别跨 VLAN、终端隔离、DNS 拦截等现场网络问题，并给出明确诊断结果。

## 3. 适用边界

### 3.1 必要条件

- 手机必须连接养老院允许访问业务服务器的员工 Wi-Fi。
- 员工 Wi-Fi 到服务器网段必须存在路由，并允许 TCP 443。
- 服务器能够访问经审批的外部 DNS 更新、证书和时间同步服务。
- 手机能够解析方案使用的真实域名。

如果合同要求“互联网完全中断后，新手机仍能扫描同一个二维码访问”，院方还必须提供同名的内部 DNS 解析或允许部署本地 DNS 转发。仅依赖公共 DNS 时，本地业务不会因断网停止，但尚未缓存域名的新手机可能无法完成首次解析。

### 3.2 本方案不能自动解决的问题

- 手机处于访客 Wi-Fi，且访客网络禁止访问院内服务器。
- 多栋楼使用相互独立、互不路由的家用路由器。
- Wi-Fi 开启客户端隔离，禁止终端访问其他内网设备。
- 院方防火墙禁止手机到服务器的 TCP 443 流量。
- DNS 安全设备拦截解析到私有 IP 的公共域名。

出现上述情况时，需要院方调整网络策略、提供内部 DNS，或者部署专用网络/中继。单纯修改二维码或增加广播协议无法绕过网络隔离。

## 4. 总体架构

### 4.1 本地业务服务

- Web 应用、API、数据库、文件、模型和审计日志均运行在本地服务器。
- 正式入口仅开放 HTTPS 443，不向员工终端暴露数据库或管理端口。
- 服务监听院内网卡；公网侧不配置端口映射、反向隧道或云端代理。
- 管理界面显示当前域名、当前内网 IP、DNS 更新时间、证书状态和网络诊断结果。

### 4.2 DHCP 地址获取

- 服务器启动后通过 DHCP 获取 IP、网关和 DNS 配置。
- 不在服务器操作系统中写死 IP。
- 支持院方可选配置 DHCP 保留；即使没有保留，动态 DNS 仍能处理地址变化。
- 设备只发布经过校验的院内 IPv4 地址；IPv6 未完成现场验证前不发布 AAAA 记录，避免客户端优先走不可达的 IPv6。

### 4.3 固定域名

每个养老院或每台设备使用独立、不可猜测的子域名，例如：

```text
yl-a7k3.edge.example.com
```

- 不使用 `.local` 作为主域名，因为 `.local` 属于 mDNS，跨网段和不同手机浏览器的行为不一致。
- 域名中不包含养老院全名、居民信息或精确地址。
- 二维码只编码该固定 HTTPS URL，不编码 IP 地址。
- 二维码下方印刷“请连接院内员工 Wi-Fi 后扫码访问”。

### 4.4 动态 DNS 更新程序

服务器运行一个与业务系统隔离的轻量更新程序：

1. 启动时读取当前默认路由对应的院内 IPv4 地址。
2. 地址变化后等待短暂稳定窗口，避免网卡切换导致频繁更新。
3. 使用仅能修改本设备 DNS 记录的独立凭据调用 DNS API。
4. 将 A 记录更新为当前内网 IP，TTL 建议设置为 60 至 300 秒。
5. 查询权威 DNS 验证记录是否生效。
6. 更新失败时指数退避重试，并在本地管理页面报警。
7. 定期核对 DNS 记录，处理人工误改或短暂 API 故障。

更新程序只能读取网卡信息和自己的凭据，不授予数据库、业务文件、照片目录或模型目录的读取权限。

### 4.5 HTTPS 证书

- 每个机构使用独立域名和独立证书，避免将同一个通配符证书私钥复制到所有设备。
- 使用 ACME DNS-01 完成签发和续期，不开放公网 HTTP 端口。
- DNS 更新凭据与证书签发凭据分离，并限制到单个域名或最小 DNS 区域。
- 私钥加密保存，严格限制文件权限；条件允许时使用 TPM 或硬件安全模块保护。
- 到期前主动续期，连续失败时在本地管理页面产生高优先级告警。

### 4.6 可选的离线 DNS

需要保证断网后二维码仍然可用的机构，采用分域解析：院内 DNS 将同一个真实域名解析到本地服务器 IP，公共 DNS 作为联网状态下的通用解析入口。员工手机通过 DHCP 获得院内 DNS 地址，无需修改二维码。

该能力需要院方 IT 配置内部 DNS 或调整 DHCP 下发的 DNS，不能由一台普通服务器在未知园区网络中自行强制完成。

## 5. 访问流程

### 5.1 设备启动

1. 服务器从 DHCP 获取内网 IP。
2. 本地业务服务完成健康检查并监听 HTTPS 443。
3. 动态 DNS 更新程序检测 IP，并更新固定域名的 A 记录。
4. 程序验证 DNS 与 HTTPS 状态。
5. 管理页面显示“二维码入口已就绪”。

### 5.2 用户访问

1. 工作人员连接院内员工 Wi-Fi。
2. 扫描护士站或办公室张贴的固定二维码。
3. 手机查询固定域名，取得服务器当前内网 IP。
4. 浏览器通过院内网络与本地服务器建立 HTTPS 连接。
5. 登录、查询、上传和模型处理均在养老院本地完成。

### 5.3 IP 变化

1. 服务器获得新的 DHCP 地址。
2. 更新程序检测到变化并修改 DNS 记录。
3. 在 DNS TTL 和客户端缓存过期后，原二维码自动指向新 IP。
4. 目标恢复时间建议定义为 5 分钟以内。

## 6. 网络与数据安全策略

### 6.1 防火墙原则

| 方向 | 默认策略 | 例外 |
|---|---|---|
| 互联网到服务器 | 全部拒绝 | 无，不做公网端口映射 |
| 院内员工网到服务器 | 拒绝 | 允许 HTTPS 443；管理端口仅限管理员网段 |
| 服务器到互联网 | 拒绝 | 仅允许审批后的域名、IP、协议和端口 |
| 服务器到院内其他设备 | 拒绝 | 仅开放业务明确需要的目标 |

外部白名单通常包括：

- DNS API HTTPS 443。
- ACME 证书服务 HTTPS 443。
- 院方指定 NTP 服务 UDP 123，或受控 HTTPS 时间源。
- 经过审批的外部数据源 HTTPS 443。

外部数据请求中不得携带居民姓名、证件号码、健康记录、照片、房间号或能够关联个人身份的查询内容。

### 6.2 数据分类

严禁出站的业务数据：

- 居民档案、身份信息、护理记录和健康数据。
- 照片、音视频、文档和附件。
- 模型输入、模型输出、向量数据和对话记录。
- 数据库备份、业务日志和审计日志。
- 账号、口令、会话和权限信息。

允许出站的最小运维元数据：

- 不可猜测的设备编号。
- 当前私有 IP。
- DNS 记录名称、更新时间和更新结果。
- ACME 证书验证数据。
- 不包含业务字段的服务健康状态，且仅在院方明确批准后启用。

### 6.3 审计

- 所有 DNS 更新、证书签发、外部访问和防火墙拒绝事件在本地记录。
- 日志包含时间、目标、结果和调用组件，不记录业务正文和密钥。
- 支持导出“业务数据未出站”的审计报告。
- 动态 DNS 程序使用独立系统账号或容器运行，不能访问业务数据卷。

## 7. 故障与降级

| 故障 | 用户影响 | 处理方式 |
|---|---|---|
| 互联网中断，IP 未变化 | 本地业务继续运行；新手机可能无法查询公共 DNS | 已有连接和缓存继续使用；需要保证扫码入口时启用院内 DNS，否则使用 mDNS 或当前 IP 应急 |
| 互联网中断且 IP 变化 | 域名可能暂时指向旧地址 | 管理页面显示当前 IP；使用 mDNS 或维护入口应急，网络恢复后自动更新 |
| DNS API 故障 | 新 IP 暂时不能通过域名访问 | 本地重试、告警并保留旧记录 |
| HTTPS 证书续期失败 | 临近到期时产生风险 | 提前续期并高优先级告警，不允许静默过期 |
| 手机使用移动数据或访客 Wi-Fi | 无法访问私有 IP | 二维码旁提示连接员工 Wi-Fi |
| DNS 重绑定保护拦截私有地址 | 域名不能解析或被改写 | 现场验收；改用院方内部 DNS 或配置安全设备白名单 |
| 跨 VLAN 路由未放通 | 能解析但连接超时 | 院方放通目标网段到服务器 TCP 443 |
| Wi-Fi 客户端隔离 | 手机无法连接本地服务 | 使用员工 Wi-Fi 或调整 AP 隔离策略 |

辅助发现可启用 mDNS/DNS-SD，但只作为应急和诊断能力，不作为正式入口的唯一依赖。维护热点只用于服务器附近安装排障，不承担园区覆盖。

## 8. 部署流程

### 8.1 出厂准备

1. 为机构或设备生成匿名编号和唯一域名。
2. 创建最小权限 DNS 更新凭据。
3. 安装并验证动态 DNS、证书和本地业务组件。
4. 生成永久二维码及打印物。
5. 记录设备编号、域名和凭据轮换信息，不写入居民或机构敏感数据。

### 8.2 现场安装

1. 将服务器有线接入院方核心网络或指定业务网。
2. 确认服务器通过 DHCP 获取地址并能访问外部白名单。
3. 确认固定域名已解析到当前内网 IP。
4. 使用 Android 和 iPhone 从主要楼栋、护士站、办公室逐点扫码测试。
5. 检测跨 VLAN 路由、访客隔离、DNS 拦截和 TCP 443 可达性。
6. 在通过测试的员工区域张贴二维码。
7. 将网络拓扑、放通规则和测试结果纳入交付记录。

### 8.3 现场变更

- 更换路由器或 DHCP 地址池后，更新程序自动适配新 IP。
- 更换服务器时保留原域名，并安全迁移或重新签发证书和 DNS 凭据。
- 域名或设备归属变更必须经过授权并记录审计。

## 9. 验收标准

1. 服务器不配置静态 IP也能完成启动和域名更新。
2. 冷启动后 5 分钟内，固定二维码能够从所有约定员工区域打开登录页。
3. 人工触发 DHCP 地址变化后，原二维码在 5 分钟内恢复访问。
4. Android 和 iPhone 的主流浏览器均显示有效 HTTPS 证书，无安全警告。
5. 断开互联网后，本地应用、数据库和模型继续运行；通过院内 DNS 或约定的应急入口验证登录、查询、录入和文件访问。
6. 公网扫描无法直接连接服务器，院方边界不设置入站端口映射。
7. 出站白名单之外的访问全部被防火墙拒绝。
8. 动态 DNS 更新程序无法读取业务数据库和业务文件。
9. 抽查网络流量，确认没有居民数据、照片、业务正文或模型内容出站。
10. 对 DNS 失败、证书续期失败、跨 VLAN 不通等情况能够给出明确告警。

## 10. 实施阶段建议

### 阶段一：概念验证

- 选择一家 DNS 服务商完成单设备动态 A 记录更新。
- 使用真实域名和 DNS-01 签发独立 HTTPS 证书。
- 验证 Android、iPhone、常见路由器以及手机私有 DNS/DoH 场景。
- 验证公共 DNS 返回私有 IP 是否被目标网络的重绑定保护拦截。
- 模拟 DHCP 地址变化、DNS API 中断和互联网中断。

### 阶段二：产品化

- 将动态 DNS 程序与业务系统隔离并应用最小权限。
- 增加状态页面、告警、重试、凭据轮换和本地审计。
- 建立每台设备独立域名、证书和 DNS 权限的生产流程。
- 制作二维码、现场网络检查表和院方 IT 对接说明。

### 阶段三：试点交付

- 在一家养老院完成多楼栋、多 AP 和跨 VLAN 测试。
- 记录真实网络拓扑和失败类型，完善自动诊断。
- 通过抓包和防火墙日志验证业务数据不出站。
- 试点验收后再扩大部署范围。

## 11. 最终推荐

正式入口采用“唯一真实域名 + 永久二维码 + 动态 DNS + 独立 HTTPS 证书”。服务器使用 DHCP，不要求设备端固定 IP；mDNS/DNS-SD 仅作为辅助；不建设公网反向代理，不把业务流量送入云端。

这套方案能够实现“无需安装 App、无需输入 IP、扫码即用、业务数据完全本地处理”。同时必须在合同和交付说明中写明：院内员工网络需要能够解析该域名并访问服务器 TCP 443；跨 VLAN、访客隔离和多个独立 NAT 网络不属于 DNS 能单独解决的问题。
